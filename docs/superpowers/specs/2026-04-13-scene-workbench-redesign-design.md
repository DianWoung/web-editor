# 场景工作台与精简编排页设计

## 背景

当前场景模块已经拆出：

- `/scenes`：场景管理
- `/scenes/:sceneId/preview`：只读预览
- `/scenes/:sceneId/overview`：运行态总览
- `/editor?sceneId=...`：场景编排

但当前流程仍然偏散，主要问题有 5 个：

1. `/scenes` 更像列表页，不像真正的工作台入口。
2. 新增场景只收 `name`，还没有 `remark`，与用户要的最小建档不匹配。
3. 编辑页仍保留偏工具化、偏调试的底部区域，主画布不够聚焦。
4. 预览页同时承担了过多“说明性内容”，视觉重心不够明确。
5. 删除流程没有收敛成唯一危险操作入口，后续扩展时容易分散。

本轮目标不是重写场景编排能力，而是重构“新增、编辑、预览、删除”的主流程，让场景模块更像真实交付里的业务工作台。

## 目标

本轮设计需要达成：

1. `/scenes` 成为场景唯一主入口，并升级为轻量工作台。
2. 新增场景采用“最小建档”流程：先填写 `场景名称`、`场景备注`，再进入编辑。
3. 编辑页只保留场景级元信息中的：
   - `场景名称`
   - `场景备注`
4. 预览页只保留：
   - 3D 效果查看
   - 视角操作
   - 流动状态开关
   - 轻量摘要信息
5. 删除动作只在场景工作台内出现，并强制二次确认。
6. 保留运行态总览入口和设备详情跳转能力，便于后续接入实时设备数据。

## 非目标

本轮不包含：

- 重写场景编排核心 store
- 新增场景版本历史或回收站
- 调整设备详情页运行态合同
- 改写 3D 预览/总览底层渲染壳
- 引入复杂模板场景创建流程

## 设计原则

### 1. 场景管理优先于页面管理

用户的操作对象应该始终是“场景”，而不是“先进入某个页面，再在页面里找场景”。

因此 `/scenes` 需要承担四种统一入口动作：

- 新增
- 编辑
- 预览
- 删除

运行态总览保留，但不作为本轮核心管理动作，而是作为场景的扩展查看入口。

### 2. 编辑页只做编排

编辑页应该是“编排台”，不是“调试工具页”或“数据检查台”。

场景元信息只保留在顶部一行：

- 场景名称
- 场景备注
- 保存
- 撤销
- 返回场景管理

除此之外，编辑页主体只为三件事服务：

- 选设备
- 摆设备/连管线
- 改对象属性

### 3. 预览页只看效果

预览页不是第二个管理页，也不是运行态总览页。它的职责应收敛为：

- 只读查看场景布局效果
- 操作视角
- 预览流动状态
- 看少量摘要

不在预览页放删除入口、复杂列表或可编辑表单。

### 4. 危险操作单点收敛

删除场景属于危险操作，应只在一个地方出现：

- `/scenes` 工作台中的场景条目动作区

删除后必须二次确认，不做回收站，不在编辑页或预览页重复出现。

## 信息架构

### 路由

本轮不新增场景顶层路由，只重构现有路由职责：

- `/scenes`
  - 场景工作台
- `/scenes/:sceneId/preview`
  - 只读效果预览
- `/scenes/:sceneId/overview`
  - 运行态总览，保留设备详情跳转
- `/editor?sceneId=...`
  - 场景编排

### `/scenes` 工作台结构

`/scenes` 从“列表页”升级为“轻工作台”，由 4 张卡片组成：

1. `新建场景卡`
2. `场景列表卡`
3. `选中场景摘要卡`
4. `状态卡`

#### 新建场景卡

字段只保留：

- `场景名称`
- `场景备注`

主动作：

- `创建并进入编辑`

不再在创建阶段放：

- 场景 JSON
- 模板选择
- 运行态相关字段
- 场景发布类按钮

#### 场景列表卡

每个场景条目显示：

- 名称
- 备注摘要
- 更新时间
- 设备数
- 管线数

每个条目动作保留：

- `运行态`
- `预览`
- `编辑`
- `删除`

其中：

- `运行态` 进入 `/scenes/:sceneId/overview`
- `预览` 进入 `/scenes/:sceneId/preview`
- `编辑` 进入 `/editor?sceneId=...`
- `删除` 弹确认层

#### 选中场景摘要卡

只承担识别和决策作用，显示：

- 名称
- 备注
- 最近更新时间
- 设备数
- 管线数

它不承载任何复杂编辑表单，也不替代预览页。

#### 状态卡

只显示当前状态，例如：

- 当前选中场景
- 最近编辑时间
- 当前是否为工作场景

保持轻量，避免演变成 dashboard。

## 主流程设计

### 新增流程

目标：把新增从“直接创建空壳文件”变成“最小建档”。

流程：

1. 用户进入 `/scenes`
2. 在 `新建场景卡` 中填写：
   - 场景名称
   - 场景备注
3. 点击 `创建并进入编辑`
4. 后端创建命名场景记录与空场景文件
5. 前端跳转到 `/editor?sceneId=...`

创建结果应至少包含：

- `sceneId`
- `name`
- `remark`
- `updatedAt`

### 编辑流程

目标：让编辑页从“工具页”收敛成“编排页”。

编辑页顶部保留：

- 场景名称输入框
- 场景备注输入框
- 保存按钮
- 撤销按钮
- 返回场景管理

编辑页主体保留：

- 左侧设备库
- 中间画布
- 右侧属性面板

编辑页应移除或默认隐藏：

- 底部 `SceneJsonToolbar`
  - 导出 JSON
  - 导入 JSON
  - 加载示例场景
  - 清空场景
  - 压测按钮
  - 大段工具提示
- 底部 `EditorDeck`
  - `场景对象`
  - `连接拓扑`
  - `原始 JSON`

这些内容如果后续仍需要，应转成开发态工具入口，而不是正式编排页面主体。

### 预览流程

目标：让预览页只负责“看效果”。

预览页左侧只保留：

- 场景名称
- 场景备注
- 最近更新时间
- 设备数
- 管线数
- 流动状态开关
- 返回场景管理
- 进入编辑

预览页主区域：

- 三维只读画布

预览页应移除：

- 设备长列表
- 管线长列表
- 删除按钮
- 任何可编辑表单

### 删除流程

目标：危险动作只在一个地方出现。

流程：

1. 用户在 `/scenes` 的场景条目上点击 `删除`
2. 弹出二次确认层
3. 确认文案至少包含：
   - 场景名称
   - 删除不可恢复
4. 用户确认后执行删除
5. 列表刷新，若删的是当前选中场景，则切换到最近一个可用场景

删除入口不再出现在：

- 编辑页
- 预览页
- 运行态总览页

## 数据模型调整

### 场景元数据新增 `remark`

当前场景列表只存：

- `id`
- `name`
- `updatedAt`
- `deviceCount`
- `pipeCount`

本轮需要把场景备注纳入正式元数据：

- `remark`

影响范围包括：

- 前端 `sceneLibraryItemSchema`
- 后端 `sceneLibraryItemSchema`
- `/api/scene/library` 响应
- `POST /api/scene/library`
- `PUT /api/scene/library/:sceneId`
- 场景库索引文件 `index.json`

### 命名场景创建与更新接口

当前创建命名场景接口是：

- `POST /api/scene/library`
  - body: `{ name, scene }`

当前更新命名场景接口是：

- `PUT /api/scene/library/:sceneId`
  - body: `scene`

这不足以支持在编辑页保存 `name + remark + scene`。

本轮建议改成：

- `POST /api/scene/library`
  - body: `{ name, remark, scene }`
- `PUT /api/scene/library/:sceneId`
  - body: `{ name, remark, scene }`

这样场景元信息和编排内容可以在一次保存动作中一起落盘。

## 测试要求

### 前端

至少覆盖：

1. `/scenes`
   - 创建场景时提交 `name + remark`
   - 列表渲染 remark 摘要
   - 删除动作触发二次确认
2. `/editor`
   - 顶部场景名称/备注可加载
   - 保存时提交元信息与 scene
   - 不再渲染旧底部工具区
3. `/scenes/:sceneId/preview`
   - 渲染轻量摘要
   - 不再渲染设备/管线明细长表

### 后端

至少覆盖：

1. 创建命名场景时 remark 持久化
2. 更新命名场景时可同时更新：
   - name
   - remark
   - scene
3. 场景列表返回 `remark`
4. 删除命名场景接口与确认后端行为

## 兼容性与迁移

历史 scene library index 中没有 `remark`。本轮需要兼容旧数据：

- 旧记录默认 `remark: ""`
- 读取旧 `index.json` 时自动补空字符串
- 写回时统一落成新结构

这样可以避免升级后旧场景列表读失败。

## 推荐实现策略

推荐按三步推进：

1. 先改 scene metadata 合同  
   把 `remark` 和更新 payload 定下来。

2. 再改 `/scenes` 工作台与删除流程  
   把新增/删除入口统一。

3. 最后收缩 `/editor` 和 `/preview`  
   把页面负担降下来，并补回归测试。

这样改动路径清晰，也不容易把现有场景编排主链路打断。
